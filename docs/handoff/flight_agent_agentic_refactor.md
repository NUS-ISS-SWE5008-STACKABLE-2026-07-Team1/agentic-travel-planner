# Flight Agent — what changed on 2026-08-23, and why

Short version for the team. Full detail in
[`docs/flight_agent/design.md`](../flight_agent/design.md); live measurements in
[`mode-eval.md`](../flight_agent/mode-eval.md).

Nothing here changes another agent's contract. `AgentFinding`, the A2A messages
and the graph shape are untouched, so Hotel, Accessibility, Risk & Advisory and
the orchestrator are unaffected — with one deliberate exception, noted below.

---

## 1. The prompt-only path could invent flights. It can't now.

**The problem.** When no inventory covered a route, the agent fell back to asking
the model directly. It returned flight numbers, times and prices that did not
exist, in `options` — the part the UI renders most prominently — labelled only by
a warning further down. The guardrail meant to catch invented flight IDs could not
run there at all, because the list it checks membership against doesn't exist on
that path. That path also had **no input screening and no output screening**.

**The fix.** Both screening hooks are now wired, and a postprocess strips any
concrete flight the model produces. The path still gives useful route guidance
("this route is usually one stop, these carriers fly it, expect this range") — it
just cannot name a specific flight. Enforced in code, not by asking the model
nicely.

**This was applied to `hotel_transport_agent` in the same change**, because the two
modules are near-duplicates and a previous guardrail fix had to be applied twice
after one was missed. `tests/test_agent_parity.py` now fails if either agent
regains the gap alone. That's the one file outside Flight that this touched.

## 2. The agent can now search more than once — but only when it needs to

The search/rank/relax logic is now callable as three tools, and the model decides
when to use them. Ranking is still done by ordinary code; the model chooses *what
to search for*, never what a flight says.

**It is not on for everyone.** `FLIGHT_AGENT_MODE=auto` is the default: run the
single-shot path as before, and open the loop **only when the deterministic search
leaves a leg empty**. That check costs no model call.

Why not always on — measured over 36 live runs against gpt-4o:

| mode | median | options found | runs returning options |
|---|---|---|---|
| `structured` (old behaviour) | 5377ms | 32 | 8/12 |
| **`auto` (new default)** | **6046ms** | **44** | **10/12** |
| `agentic` (always loop) | 8525ms | 44 | 10/12 |

The loop's benefit was concentrated in **one** case — a stocked route on an
unstocked date went from **0 options to 6**. Every other scenario got an identical
answer for 2–4 extra seconds. Always-on would have taxed every request for a
benefit most never see; `auto` gets the full benefit for +669ms on the median.

Relevant to everyone: the four specialists run in parallel and the plan waits for
the slowest, so Flight's latency is the whole plan's latency when Flight is
slowest. That's why this was measured before being switched on, and it's why
`FLIGHT_AGENT_MODE=structured` exists as a one-variable revert.

## 3. Seed data now has a second hub (London)

**Expect the pushback, so here it is up front: a Singapore-only dataset would have
been sufficient for a Singapore-centred demo. This is not a correctness fix.**
The argument for it is narrow and I'd rather state it plainly than oversell it.

Before this, **every row in the dataset had Singapore at one end**. That is a
property of the dataset's *shape*, not its size — and adding more Singapore
flights would not have changed it. The consequence: any trip that didn't touch
Singapore had *zero* data and fell to the prompt-only path, which (before item 1)
is exactly where the system invented flights. So the failure mode the guardrail
work exists to prevent was reachable by almost any trip a marker or demo audience
might type.

What the second hub buys:

- **A whole second family of trips can be answered from real data** — London to
  Paris, Rome, New York, and so on. 60 routes now, 24 of which don't touch
  Singapore.
- **Evidence the design isn't accidentally single-hub.** Multi-airport handling,
  route resolution and ranking are now exercised somewhere other than the hub they
  were written against. `london_hub` is a scenario in the eval above and behaves
  identically to the Singapore ones.

What it cost:

- ~190 generated rows (280 → 472).
- **Zero changes to existing rows.** A separate RNG stream and flight-number range
  mean the original 280 regenerate byte-identically — verified as 192 insertions,
  0 deletions. Only *new* airport pairs were added, so no golden scenario could be
  reordered and **no test expectation was rewritten**.
- No maintenance burden: it's generated by `scripts/generate_flight_seed_csv.py`
  and fully deterministic.

What it explicitly does **not** do:

- It does not "solve" coverage and was never meant to. 60 of `places.py`'s 64,262
  ordered city pairs are stocked. Chasing coverage is unwinnable — full coverage at
  this density is roughly 8.1M rows — which is exactly why item 1 (making the
  no-data path safe) matters more than the dataset's size. Some routes are left
  unstocked *on purpose* so the no-data path stays reachable and its regression
  tests keep exercising it.

If the team would rather revert to one hub, it's a contained change: delete
`HUB_ROUTES` from the generator and regenerate. Nothing else depends on it.

## 4. What this does not do

- **Doesn't change any other agent's contract.** No schema, A2A or graph changes.
- **Doesn't turn on live flight data.** Still `FLIGHT_INVENTORY_SOURCE=seed`.
  Everything measured here is on seed, where re-searching is free; on Duffel each
  search is billed and the budget bounds `fetch` calls, not supplier searches.
- **Doesn't fabricate anything, measured.** 120 options across 36 live runs, zero
  naming a flight no provider returned. Options are built by code from provider
  rows, so this is structural rather than filtered.

## 5. Known gaps, stated rather than buried

- **`rank_flights` is built and tested but the model never calls it.** The seed
  generator puts exactly two flights in every route+date group, so there is never a
  meaningful list to reorder. Fixing it properly means more flights per date on the
  Singapore routes too, which reorders golden scenarios — so it needs its own
  change with the expectations regenerated under review. Deliberately postponed.
- **Estimated output is still distinguished only by a warning list**, not visually
  in the UI. Worth a frontend follow-up.
- **`agent_relaxation_applied` still records model-generated free text** in an
  audit trail meant to hold counts only. Pre-existing; worth narrowing.

## 6. If something looks wrong

- `FLIGHT_AGENT_MODE=structured` restores the previous behaviour exactly, one
  environment variable, no code change.
- `python scripts/flight_mode_eval.py --repeats 2 --spike` re-runs the measurements
  above. It hits a real model and costs money, so CI never runs it.
- Traces carry the new events: `agent_tool_called`, `agent_tool_rejected`,
  `agent_budget_exhausted`, `agent_loop_completed`, `agent_path2_options_stripped`,
  `agent_loop_unavailable`. All counts and codes, no traveller text.

666 tests passing, semgrep clean on 9 rules, golden scenarios unchanged.
