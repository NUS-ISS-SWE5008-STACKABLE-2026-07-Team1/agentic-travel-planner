# Structured plan sections

Status: designed
Date: 2026-09-13

## Problem

A finished plan renders as a title, a summary, one flat `plan.itinerary` list
under "Suggested itinerary", and then three generic list sections. Everything a
specialist actually found — the flight it priced, the hotel it ranked, the
airport transfer it costed — is either paraphrased into an itinerary string by
the orchestrator or not shown at all.

The exception proves the point: `app.js:512-590` already reaches past the plan
into `response.agent_findings` to render the accessibility agent's evidence as
cards, because the plan's own fields could not carry it. That one bespoke block
is the shape the other specialists need too.

Two consequences. A traveller cannot see which flight the plan means, only the
orchestrator's sentence about it. And with selective dispatch now live, a
hotel-only plan looks the same as a plan whose flight search returned nothing.

## Scope

In scope: rendering explicit per-specialist sections from the findings the
specialists already return, in a fixed order, present only when that specialist
ran.

Out of scope, explicitly:

- **Changing what the orchestrator writes.** `plan.itinerary` stays exactly as
  it is. It is the only artefact that reasons ACROSS specialists — sequencing a
  flight, a check-in and a transfer into a trip — and nothing else produces it.
- **Structured section fields on `TravelPlan`.** Considered and rejected: the
  model would rewrite specialist facts into those fields, so a price could drift
  from what the specialist actually found. Sections are projections of findings,
  never regenerations of them.
- **Persisting the sections.** They are derived from rows already stored.
  Storing both would let the two disagree.

## Decisions

| Decision | Choice | Rejected alternative |
| --- | --- | --- |
| Section content | Projected from `agent_findings` | Generated by the orchestrator |
| Hotel vs transport | A `category` on `Option`, set by the builder | Parsing the description text |
| Where the logic lives | Server-side, `sections.py` | Grouping inside `app.js` |
| Delivery | A derived `sections` field on the response | Frontend derives it per client |
| Existing itinerary | Unchanged, sections below it | Sections replace it |
| A section with no options | Still rendered, summary only | Omitted |

Three of these earn an explanation.

**The category is the specialist's claim, not a guess.** `_transport_to_option`
writes `f"{option.mode} — {option.name}"` into the description, so a prefix match
could split hotels from transfers today. That would make the UI depend on a
string format nothing enforces — the same class of fragility as the phone regex
that matched ISO dates. The two builders already know which is which; they
should say so in a field.

**The logic goes server-side because the frontend cannot be tested.** This repo
has no JS test harness and no browser driver, which has left every frontend
change this month verified only by eye. Ordering, grouping and omission are
exactly the rules that go wrong silently, so they belong where pytest can reach
them. `app.js` then renders what it is handed.

**A section with no options still renders.** An agent that ran and found nothing
has said something, and the traveller needs to know it looked. Silence is
indistinguishable from never having been asked — the same reasoning as
`disclose_unconsulted`.

## Flow

```
specialists                     each returns AgentFinding(options=[Option(category=…)])
     │
     ▼
plan_sections(findings)         pure: findings in, ordered sections out
     │   flights                ← flight_agent options, category "flight"
     │   hotel                  ← hotel_transport_agent options, category "hotel"
     │   arrival & transport    ← hotel_transport_agent options, category "transport"
     │   accessibility evidence ← accessibility_agent
     │   risk & advisory        ← risk_advisory_agent, ALWAYS LAST
     │
     │   a section exists only if its finding exists, so a hotel-only plan
     │   has no flight section with no `if scope ==` anywhere in the renderer
     ▼
PlanResponse.sections           derived at response time, never stored
     ▼
app.js                          renders in the order given, below the itinerary
```

## Components

### `flaskapp/travel_ai/schemas.py`

```python
category: Literal["flight", "hotel", "transport", "accessibility", "advisory"] | None = None
```

on `Option`. Additive and defaulted, so every stored row, golden scenario, bias
audit fixture and A2A artifact stays valid untouched — the discipline the city
and `plan_scope` fields both used. `None` means an option from a builder that
does not yet classify itself; it falls into its agent's default section rather
than disappearing.

### The three builders

`hotel_transport_agent/agent.py:143` `_hotel_to_option` → `"hotel"`, and
`:157` `_transport_to_option` → `"transport"`. `flight_agent/agent.py:193` →
`"flight"`. Each already knows what it is building; this only records it.

The accessibility and risk agents build options through the model rather than a
builder, so their options stay `None` and are grouped by their agent.

### `flaskapp/database.py`

`options` gains `category TEXT` — nullable, because every row written before
this change genuinely has no category and NULL says exactly that. One
`ADD COLUMN` in `initialize()` alongside the `plan_scope` migration, and one
column in `save_plan`'s INSERT.

Note the distinction this draws. The **category** is persisted: it is a fact the
specialist asserted about an option it produced, and the audit trail should hold
it. The **sections** are not: they are a projection of rows already stored, and
keeping a second copy would let the two disagree.

### `flaskapp/travel_ai/sections.py` (new)

```python
SECTION_ORDER: tuple[tuple[str, str, str | None], ...]   # (title, agent, category)

@dataclass(frozen=True)
class PlanSection:
    title: str
    agent: str
    summary: str
    options: list[Option]

def plan_sections(findings: list[AgentFinding]) -> list[PlanSection]
```

Pure — findings in, sections out. No model, no IO, no config, so the rules that
matter are testable without a graph or a browser.

Order is fixed by `SECTION_ORDER`, not by the order findings arrive. Specialists
run in parallel and the reducer concatenates them as they finish, so arrival
order is nondeterministic; a traveller must not see the sections shuffle between
two runs of the same trip. Risk & advisory is last because advisories are read
after the plan they qualify.

One finding can yield two sections: `hotel_transport_agent` splits into hotel and
transport by category, sharing its summary.

### API and frontend

`PlanResponse` gains `sections: list[PlanSection]`, populated in `service.py`
beside the existing `agent_findings`. Derived at response time; `save_plan` is
unchanged.

`app.js` renders each section under the itinerary, reusing the card markup the
accessibility block already uses. That bespoke block is folded into the general
mechanism rather than left beside it — it becomes one section of five, and
leaving both would mean two renderers for the same data.

## Error handling

| Condition | Behaviour |
| --- | --- |
| Specialist did not run | No finding, therefore no section. Nothing to special-case |
| Finding with no options | Section renders with the summary alone |
| Option with `category=None` | Falls into its agent's default section |
| Plan withheld by the output gate | Sections still render: findings passed their own agents' gates, which is why `withheld_plan` already shows their summaries |
| No findings at all | Empty list; the itinerary renders as it does today |

## Known limitations

- **Frontend rendering stays unverified.** The projection is tested; what
  `app.js` does with it is not, for want of a JS harness. Adding one would make
  this and the last three frontend changes checkable.
- **`category` is only as good as the builder.** An option built somewhere new
  without setting it lands in the agent's default section — visible, but not in
  the section a reader might expect.
- **Sections do not sequence.** They list what each specialist found; the
  day-by-day ordering remains the orchestrator's narrative, and nothing checks
  the two agree.

## Testing

- `plan_sections` order is fixed regardless of the order findings arrive.
- A missing agent produces no section for it; a hotel-only finding set produces
  hotel and transport sections and no flight section.
- One `hotel_transport_agent` finding splits into two sections by category.
- A finding with no options still produces a section carrying its summary.
- Risk & advisory is last in every combination.
- `Option` without `category` validates, and existing golden scenarios and the
  bias audit are unaffected.
- `save_plan` round-trips `category`, and a row written before the column exists
  reads back as NULL.
