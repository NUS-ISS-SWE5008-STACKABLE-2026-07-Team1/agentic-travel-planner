How the Accessibility Agent works

From traveller input to evidence-grounded recommendations, showing the official A2A handoff, external research, safety controls, and final response.

End-to-end information flow

Guardrails surround the model rather than relying on prompting alone. Validation happens before execution, retrieved content is treated as untrusted, and generated claims are checked again before delivery.

Accessibility guardrail layers

Open each layer for the control, its purpose, and the behaviour when it fails.

Input Schema, size and sensitive fields

Rejects malformed or oversized requests and unsupported sensitive ranking attributes before any model or search call.

Input Prompt injection and L2 screening

Normalizes all user-controlled text, detects explicit injection patterns, and optionally uses a semantic classifier for obfuscated attacks and out-of-scope requests.

A2A Protocol boundary validation

Requires exactly one JSON data part, validates the TravelRequest again, and reports typed A2A errors instead of starting a phantom task.

Safety Accessibility preflight

Blocks injection, toxic language and high-risk disability stereotypes. A blocked request bypasses the model and returns confidence zero with human review required.

Privacy Requirement abstraction

Maps raw needs to functional categories such as mobility, vision or hearing. External queries use generic functional terms instead of raw medical descriptions.

Retrieval Bounded web search

Uses a fixed HTTPS provider endpoint, timeouts, two attempts, four results per query, at most four categories and eight total evidence records.

Retrieval URL and source controls

Accepts public HTTPS links without embedded credentials, removes duplicates, and classifies sources as official, specialist, crowdsourced or unknown.

Evidence Untrusted-content sanitation

Screens titles and excerpts for injection, toxicity and bias. Unsafe records are removed and the rejection count is disclosed in warnings.

Output Structured response validation

Requires the model to return the AgentFinding schema. Malformed output fails instead of being displayed as a recommendation.

Output Evidence ID and exact-link enforcement

A claim retains a URL only when it cites a valid evidence ID that maps to the exact retrieved URL. Invented and altered links are removed.

Output Status, rating and confidence controls

Downgrades unsupported “verified” claims, recalculates accessibility ratings, and caps confidence when evidence is missing, partial or unknown.

Output Accessibility veto and human review

Removes known-unsuitable options, records the unmet requirement, and generates specific questions for suppliers when evidence is incomplete.

How evidence changes the response

Grounded

Evidence ID and exact URL support the feature. The option can be marked verified, normally up to a deterministic 4/5 rating.

Uncertain

Evidence is missing, partial, conflicting, crowdsourced or unknown. Confidence is reduced and direct supplier confirmation is required.

Requirement unmet

The option receives an accessibility veto, is removed from recommendations, and is disclosed to the orchestrator as unsuitable.

Fan-in and user delivery

The Accessibility Agent returns an A2A agent-finding artifact. The orchestrator combines it with the other specialists, runs final output assurance, copies validated accessibility URLs into the plan, stores the result and audit trace, and displays the response in the chatbot.

Input requirement: accessibility needs must be placed in traveller_accessibility_needs or accessibility_needs. Text stored only in preferences is safety-screened but may not become a formal accessibility requirement.
