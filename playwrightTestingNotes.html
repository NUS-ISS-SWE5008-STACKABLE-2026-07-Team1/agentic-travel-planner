00

Why Playwright fits this app

This is a genuinely good match, not just "a testing tool that happens to work." The app is server-rendered Flask + Jinja2 with full-page navigation — every route change is a real page load, and there's no client-side router or reactive state to fight. That's exactly the shape Playwright is built for: it drives a real browser against real HTTP responses, so it needs no framework-specific test utilities at all.

Confirmed before recommending this

There is no existing frontend test infrastructure in this project — no JS test framework, no browser-driven fixtures. tests/conftest.py exists only to stub the LLM for the flight-agent backend tests. This is a green field, not a migration.

01

Setup — stay inside the existing pytest workflow

Use pytest-playwright, not the Node-based Playwright Test runner. The project already standardizes on pytest (pytest -q per CLAUDE.md) — a second test runner in a second language would be one more thing to keep green, for no real benefit here.

Put these under a new tests/e2e/ directory — they're categorically different from everything else in tests/, which calls Flask's in-process test client. Playwright needs an actual running server, so the missing piece is a live_server fixture.

The one new fixture this needs

  • Boot create_app() pointed at a temp SQLite path, never instance/travel_planner.sqlite3 — that file is the real dev DB and is already flagged elsewhere as something E2E runs must not touch.
  • Run it on a background thread (or process), yield its base URL, tear it down after the test session.
  • Session-scoped, so the server starts once per test run, not once per test.
02

Two testing tiers — pick based on what you're testing

Frontend-only (the bulk of coverage)

Intercept /api/v1/* with page.route() and return canned JSON. Tests app.js/intake.js's actual job — DOM rendering, the poll loop, form validation — fast and deterministic, zero dependency on a real LLM.

Real end-to-end (a handful of smoke tests)

Full stack, live server, LLM provider swapped for a stub (the app already abstracts LLM_PROVIDER/LLM_MODEL). Keep these to 2–3 tests that prove the pipeline still wires together — not where detailed coverage lives.

Why frontend-only is the primary tier, not an afterthought

Real planning takes roughly 75 seconds against a live model. A suite that runs full E2E for every case would be slow, flaky, and expensive to run in CI — the mocked tier is what actually stays fast enough to run on every push.

03

The login problem

Checked directly against routes.py and database.py rather than assumed. Login just sets a handful of keys on Flask's signed-cookie session — session["authenticated"] = True, user_id, user_email, etc. (routes.py:47-52) — backed by authenticate_user() / create_user(). Three options, in order of how much of the login flow you want exercised.

  1. Test login itself: seed a user, drive the real form. Call create_user(name, email, generate_password_hash(pw), country, birthday) directly against the test DB, then have Playwright fill and submit the real / form once. This is the only option that actually exercises the login page.
  2. Reuse that session across every other test. Log in once via option 1, then context.storage_state(path="auth.json") to save cookies. Every other test's browser context loads storage_state="auth.json" instead of logging in again — the standard Playwright pattern, and it maps cleanly here since the whole session is one cookie.
  3. Skip the UI for tests that aren't about login. Mint a valid session cookie in Python and inject it before navigating. Fastest option, and the right default for anything that just needs to be authenticated.
CSRF needs no special handling

Playwright drives a real browser executing the real page JS, so the CSRF meta tag / hidden field gets regenerated normally by Flask-WTF on every page load, regardless of how the session was established. No workaround needed here — unlike scripting raw HTTP requests, where you'd have to fetch the token yourself first.
