Agentic Travel Planner · Engineering Walkthrough

From browser to plan, and back again.

The two halves of the system that bracket the specialists: the Flask + vanilla-JS frontend a traveller actually touches, and the Orchestrator Agent — which has two jobs, one before the specialists run and one after. Companion to flightAgentExplained.html.

The pattern to carry through both halves

The model produces; Python decides. Intake uses a model to read the traveller, but ordinary Python decides what is still missing. Synthesis uses a model to write the plan, but ordinary Python decides whether it ships. Colour coding below: teal = deterministic, amber = model, clay = guardrail.

Part I

The Frontend

Server-rendered Flask templates, Bootstrap from a CDN, and three plain JavaScript files. There is no framework, no bundler, and no build step — which is worth knowing before you go looking for one.

01

The stack, and what is deliberately absent

LayerWhat it is
TemplatesJinja2, 5 files in flaskapp/templates/
CSSBootstrap 5.3.8 from jsDelivr (SRI-pinned) + static/css/app.css (224 lines) for the Atlas identity
FontsDM Sans (body) + Manrope (headings), via Google Fonts @import
JSapp.js (1,277 lines), intake.js (267), no dependencies
FormsFlask-WTF (LoginForm, RegistrationForm) for the auth pages only

Everything past sign-in is built by hand with document.createElement and fetch. No client-side templating, no virtual DOM, no state library. The trade is legibility for a small team over ergonomics at scale — and for a page whose main job is polling a status endpoint and rendering a plan, that trade holds.

One design decision visible in the markup

city_options is embedded directly into main.html rather than fetched, so the dependent city <select> repopulates instantly and the form still works if a later request fails. It is public reference data — no per-user content — which is what makes that safe.

Two guards worth reading closely

The ?next= parameter after sign-in is the classic open-redirect surface. _is_safe_redirect restricts the target to the site's own netloc, and the call site carries a nosemgrep annotation naming that mitigation — so the suppression is justified in place rather than silently applied.

Sign-in and sign-out both call session.clear() before setting anything. That prevents session fixation: an attacker-supplied pre-login session id cannot survive into the authenticated session.

State handoff between pages

Because each page is a full navigation, the payload is carried across in sessionStorage under two keys — atlas-plan-payload (the validated request, so a refinement can resubmit it) and atlas-intake-prompt (the first message typed on /main, replayed automatically on /chat/intake).

04

The intake chat

intake.js is a conversation that ends in a validated TravelRequest. It alternates between two UI shapes: free-text bubbles, and a clarification card of exactly the fields still missing.

Traveller
submitPrompt(prompt) — renders a user bubble, POSTs to /travel-intents
Server
{ question, extracted, missing, complete } — what was read, and what is still needed
Render
advance(state) — not complete? render the card. complete? hand off.
Card
POST /travel-intents/resolve — typed answers, no model call
Handoff
POST /travel-plans → 202 — then window.location.assign(job.chat_url)
A small UX guarantee in the code

The clarification card is passed into advance() and removed only once the next step has actually succeeded. A rejected request therefore never costs the traveller the answers they already typed — the card stays, the error appears above it.

One more detail that matters for correctness, not polish: presence is what marks a field answered, but accessibility needs are sent even when blank — because that blank is how "no needs" reaches the server, and treating it as unanswered would loop the question forever.

05

The planning chat — polling a job you cannot stream

Planning takes roughly 75 seconds, so POST /travel-plans returns 202 Accepted with a request id rather than blocking. The chat page then polls two endpoints once a second, in parallel.

Two things to notice. seenEvents is a Set, so re-fetching the whole trace every second is idempotent — the activity feed appends each event once. And on completion the trace is fetched one more time, because the events written in the final second would otherwise never be rendered.

The progress bar is honest about being a guess

Two estimates, and the larger wins: elapsed time gives steady movement so the bar never looks stuck, while real agent-completion milestones let it jump ahead when work genuinely finishes early. Both are capped below 100 so only actual completion closes the bar.

Trace events become plain English

The activity feed maps raw event names and agent ids to labels and icons — the same five agents, named the way a traveller would name them:

Cancellation and session cleanup

Leaving mid-plan opens a confirmation dialog rather than silently abandoning a running job. Confirming POSTs to the cancel endpoint, then ends the request session and navigates home. A pagehide listener sends the same session-end call with keepalive: true, so closing the tab still releases the request — and navigation never waits on it.

06

Frontend security, and one deliberate omission

  1. CSRF on every mutating call. CSRFProtect is app-wide; every fetch reads meta[name='csrf-token'] and sends it as X-CSRFToken. Forms carry a hidden csrf_token field.
  2. The API blueprint has its own session gate. A before_request hook returns 401 for anything unauthenticated — so API spend and traces are protected independently of the page guards.
  3. Text is set with textContent, never innerHTML. Model-generated plan prose is rendered into the DOM, so this is the difference between output and injection.
  4. Ownership is checked server-side. get_job returns a job only when job.user_id matches the session — knowing a request UUID is not enough to read someone else's plan.

setdefault rather than assignment, so a view that deliberately needs different framing can still say so.

Known gap, tracked on purpose

There is no Content-Security-Policy header. It was the third finding from the authenticated ZAP scan and is absent deliberately, not by oversight: a CSP has to list every allowed script and style source, and getting it wrong blanks a page rather than failing loudly. It is tracked separately so it can land with its own scan run. If you add one, the Bootstrap and Google Fonts CDNs both need entries.

Part II

The Orchestrator Agent

Every other agent has one job. This one has two, at opposite ends of the request — and confusing them is the most common way to get lost in this package.

07

Two jobs, one folder

Job A · Intake — before

intake.py, intake_prompt.py, intake_schemas.py. Reads free text, works out what is missing, asks for it, and hands off a complete TravelRequest. Runs at the HTTP layer — it is not a graph node.

Job B · Synthesis — after

agent.py, prompt.py. The fan-in node. Takes four AgentFindings and writes one TravelPlan, then screens it before it ships.

The division of labour, stated in the source

From intake.py's docstring: "The model extracts what the traveller said and writes one acknowledging sentence. It does not decide what is missing. Gap detection is ordinary Python against TravelRequest's required set, so the behaviour the traveller actually feels is deterministic and testable without a model."

09

Job A — conversational intake

Exactly one model call happens in this flow, and it does exactly one thing:

Same pattern as every specialist: the traveller's text goes in a HumanMessage labelled as untrusted data, never interpolated into the system message.

Gap detection is plain Python

Three judgements in that snippet are worth naming:

  1. An impossible date pair is asked again, not rejected. Re-asking keeps the traveller inside the card with their other answers intact, rather than letting TravelRequest reject the whole thing after the card is gone.
  2. Per-traveller questions are gated on knowing the count. Asking traveller 3's age before you know there are three travellers produces a question with no meaning.
  3. None inside a per-traveller list marks a still-open slot. That is what lets two travellers with one known age produce exactly one indexed question instead of two.

And because the gaps are structured objects rather than prose, the phrasing is generated deterministically too — clarification_question just joins the labels into one sentence, with an Oxford comma for three or more.

The endpoint split follows the same logic

POST /travel-intents costs a model call, because it is reading free text. POST /travel-intents/resolve — applying the card's typed answers — is deterministic: no model call happens there at all. Answering a form field should not cost an inference.

Every free-text turn is screened before extraction

screen_prompt runs ahead of extract_intent, and it is a different gate from the one in §10 — that one validates an already-typed TravelRequest; this one screens raw prose, and carries a layer the other does not: PII redaction.

Three layers, in this order, and the order is the argument: injection detection first because it is free and either rule set can reject outright; PII redaction second, so no identifier the traveller typed ever reaches the L2 model call; L2 last, over text that is already redacted. Everything downstream — persistence, the model, the transcript the traveller reads back — uses screened.text, never the original string. (Where that persistence actually lands is covered in Part III.)

Observed in end-to-end testing

A traveller wrote "I use my credit card <number> for memberships." Redaction masked the number correctly, then L2 blocked the masked sentence as pii_exposure at confidence 1.0 — reading intent still visible in the words around the placeholder, over data that no longer existed. _screen_redacted downgrades a pii_exposure BLOCK to FLAG, but only when redaction actually fired on this text: if nothing was redacted, an L2 pii_exposure block is about a credential these rules don't cover (an API key, say), and it stands.

The injection rules were broadened the same week, and one fix is worth knowing if you've read an older version of this doc: role_play used to fire on bare "act as", which blocked ordinary phrasing like "act as our guide." It now requires an adversarial complement — act as an unrestricted/admin/developer/system/DAN — bringing this boundary in line with the per-agent detectors, which were tightened the same way earlier.

10

The HTTP boundary — three gates before a job exists

GateWhat it checksCosts a model call?
L0Payload size against MAX_INPUT_CHARS; explicitly sensitive keysNo
L1PROMPT_INJECTION regex over every free-text field; Pydantic validationNo
L2Semantic classification of already-clean textYes — one small model

The ordering is the point. L2 only ever runs on input that is already structurally sound and syntactically clean, so an oversized or obviously-injected request is rejected without an API call. And validate_request stays what it has always been: the deterministic gate, testable and reviewable with no model anywhere near it.

A FLAG verdict is deliberately not an error — it is a low-confidence suspicion that belongs in the trace, not a denial served to a traveller. Only BLOCK raises. And the ALLOW verdict is returned rather than discarded, because a trace showing the classifier ran and allowed is as much evidence as one showing it blocked.

A second boundary exists

This is the gate before a job exists — POST /travel-plans. The conversational entry point, POST /travel-intents, runs a different function (screen_prompt) with a fourth layer, PII redaction, because it screens raw prose rather than an already-validated TravelRequest. See §09.

11

The background job

jobs.py is a module-level ThreadPoolExecutor(max_workers=4) plus four dicts under one lock. Small, and worth understanding before you scale it.

Cancellation is cooperative: cancel_job sets a threading.Event, and graph.py checks it before and after every node, raising PlanningCancelled. That is why the graph wraps each specialist in a cancellable_specialist closure — a cancelled traveller stops costing money at the next node boundary rather than at the end of the run.

Two footguns recorded in the source

Job state is in-process. _jobs is a module dict, so a multi-process deployment would lose it. The database rows written by create_planning_job / update_planning_job are the durable half.

database_path is deliberately not wrapped in Path(...) — it may be a postgresql:// DSN, and Path would normalise the // away and silently turn it back into SQLite.

12

Job B — synthesis, and the last gate before a traveller reads anything

service.py seeds the graph with one A2A request per specialist, all sharing a correlation id:

The four specialists then run in parallel and their findings merge through merge_findings, a LangGraph reducer that preserves every specialist's contribution rather than letting the last writer win.

Why the output gate lives here

From agent.py's module docstring

"This is the last place text can be stopped before a traveller reads it. The specialists screen their own rationales, but their findings are then rewritten here into the prose that actually ships, and that rewrite was previously unscreened — assess_plan runs afterwards and only appends warnings, it never withholds."

Retry once, then withhold — deliberately the same shape the specialists use for a failed output gate, rather than a second failure path a reader would have to learn.

withheld_plan — degrade, don't erase

Raising here would surface as a generic "Travel planning failed" and lose the specialists' work along with it. Instead the withheld plan keeps the same contract the frontend already renders, says plainly that something was withheld, and preserves each specialist's own summary — those were screened by their own agents' output gates, so they are safe to show even when the synthesis of them was not.

One more small economy: plan_text feeds the classifier only the fields a traveller actually reads. Structured numbers are excluded deliberately — they are already constrained by TravelPlan and checked by assess_plan, so sending them to a classifier adds tokens and false-positive surface for nothing.

What the orchestrator's prompt actually asks for

Worth reading once, because several of these are policy rather than style — an Accessibility VETO may never be overridden, high-severity risk findings must be escalated rather than silently accepted, material conflicts must be preserved rather than resolved by invention, and nothing may ever be described as booked.

13

The assurance layer — deterministic checks the model cannot bypass

assess_plan runs in service.py after the graph returns. It is ordinary Python, after the model has finished, which is exactly what makes it unbypassable.

The one deliberate side effect

This is the most instructive control in the codebase, so read the reasoning rather than just the code.

Observed in end-to-end testing

A specialist's warnings do not reliably survive orchestrator synthesis. A grounded run propagated the per-option provenance note verbatim; an ungrounded one saw the flag paraphrased into a milder sentence near the bottom of the plan — semantically close, but no longer a signal any code could rely on, and easy for a reader to skim past.

Checking whether the model happened to paraphrase it would be a test of luck. So enforce_provenance_disclosure appends the statement itself, and disclosure becomes a property of the system rather than of a given generation.

This is the other end of the string the Flight Agent's Path 2 pulls on. A specialist raises the flag by putting the marker phrase into its own warnings; the orchestrator does not get to decide whether it reaches the traveller:

Change the Flight Agent's ESTIMATE_WARNING wording and this match silently stops firing. That coupling is documented at both ends precisely because nothing fails loudly when it breaks.

14

The audit chain

Every plan writes a tamper-evident JSONL trace. Each event stores the previous event's hash, so editing or reordering the file after the fact is detectable.

The lock covers hashing and writing in one critical section — specialist nodes finish concurrently, so splitting them would interleave two events and break the chain.

  • Never record prompts, API keys, or raw personal data. Traces carry enums, counts and codes. The Flight Agent's agent_path2_options_stripped event records a count of fabricated options, never the flight numbers themselves.
  • verify_hash_chain recomputes every hash and confirms each previous_hash matches the prior event — the post-response gate for anything built on the trace.
  • Trace files sit on ephemeral disk. On Render, GET /api/v1/traces/<id> 404s after a redeploy even though the same events remain in the audit_events table.

The A2A envelope is stricter than it looks

response_message and error_message both take the original request and derive the correlation id from it — and both reject a sender that was not the request's recipient. Never assemble an envelope by hand; all three constructors are keyword-only, so read their signatures rather than copying a snippet.

Adding an agent

Register the id in three places — AgentId (a2a.py), AgentFinding.agent (schemas.py), and the registry in agents/__init__.py. Define input and output as strict Pydantic models with extra="forbid". Never put prompts, secrets, chain-of-thought or unnecessary personal data in payload, error or traces.

16

A second, standards-based transport for the same agents

a2a.py's envelope is real but private — nothing outside this process can address flight_agent or open a task against it. a2a_standard.py is the interoperability boundary: it publishes Agent Cards, accepts official Agent2Agent 1.x JSON-RPC tasks, and converts JSON Data Parts into the same validated TravelRequest / AgentFinding models everything else uses.

What does not change

From the module's own docstring: "Agent reasoning remains transport-independent and is reused unchanged." Every specialist node keeps its normal synchronous signature — state -> {"findings": [...], "messages": [...]} — the same one graph.py calls. Nothing inside flight_agent/agent.py, or any other specialist, knows this transport exists.

Bridging a synchronous node into an async task

asyncio.to_thread is the whole seam. The A2A server is async because the SDK's task/event model requires it; the agents are not, because LangGraph nodes and the LLM calls in this codebase are synchronous. Rather than rewrite five agents to be async, one line moves the blocking call off the event loop per request.

The orchestrator gets its own executor, not a fifth specialist slot

OrchestratorAgentExecutor does not call a graph node — it calls TravelPlanningService.create_plan directly, via a supplied orchestrator_runner, because "run the orchestrator" over A2A means the whole plan, fan-out and synthesis included, not one node's turn. PlanResponse.model_validate is the same output contract the Flask API returns from POST /travel-plans — a second transport onto an unchanged result.

ComponentRole
build_agent_cardOne discoverable AgentCard per agent — name, skill, JSON-RPC endpoint — served at /a2a/<agent>/.well-known/agent-card.json
SpecialistAgentExecutorBridges one specialist's synchronous node to an async A2A task

Running it

Three ways to stand this up, none of which touch the Flask app's own routes:

  • python -m scripts.a2a_server — the four specialists plus the orchestrator, A2A-only, on A2A_HOST / A2A_PORT.
  • python -m scripts.run_all — flaskapp/combined.py mounts the same A2A routes and the Flask website under one Starlette app, the Flask side wrapped in a2wsgi.WSGIMiddleware. A2A routes are registered first, ahead of Flask's own catch-all mount.
  • Tests inject node_factories and an orchestrator_runner directly into create_application, so route composition is verified without any LLM credentials.
Two ways to reach flight_agent now

graph.py's in-process fan-out and this A2A server both end up calling the same flight_node. Nothing about the node's guarantees — single fetch, code-decides-ranking, grounding — changes with the transport; only how a request arrives does. See flightAgentExplained.html §01.

Part III

The Database

One file, flaskapp/database.py, that every other module above reads and writes through. It quietly supports two very different databases, and knowing why explains a handful of the footguns already mentioned in Parts I and II.

17

SQLite on a laptop, Supabase when it's live

The simple version

Every message in this chat gets saved somewhere. On a developer's own laptop it's saved into a plain file on disk (SQLite). When the app is actually running live for users, it's saved into Supabase instead — a cloud-hosted database. The app doesn't use any of Supabase's other features (its login system, file storage, etc.) — just the database part.

The reason for the switch is simple: the live server's disk gets wiped every time the app is updated or restarted. If the chat history and saved plans lived only in a file on that disk, they'd vanish without warning. Supabase's database lives somewhere separate and permanent, so the data survives even when the server itself gets rebuilt.

Behind the scenes, the code that talks to SQLite and the code that talks to Supabase is written once and shared — a small layer translates the same instructions into whatever each database understands, so nothing had to be duplicated. One thing worth knowing if you're troubleshooting: the app has to connect to Supabase through a specific address (its "session pooler"), because the more obvious address isn't reachable from where the app is hosted. See §11 for a related gotcha where the wrong kind of code accidentally sent this connection back to the local file instead of Supabase.

What's still unconfirmed

All of the above is built and tested — but building it isn't the same as switching it on. A few things still need someone to actually go and check, or do, on the live site:

  • Has the old data actually been moved over? There's a script for copying everything that existed in the old local file into Supabase. It needs to be run once, for real, against the live database.
  • Is Supabase actually turned on for the live site? The connection address has to be typed into the hosting provider's dashboard by hand — it isn't something that gets set automatically just because the code supports it.
  • Does the data actually survive a restart? The real test: sign up on the live site, restart it, and check the account is still there. That's the whole point of this change, and it hasn't been confirmed yet.

Until someone confirms these, the live app may still be quietly saving everything to the disk that gets wiped — the exact problem this change was meant to fix.
