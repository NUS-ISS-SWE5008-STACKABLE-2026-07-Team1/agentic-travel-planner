00

The one idea everything else follows from

The governing idea

Code decides which flights; the model only explains the decision.

domain.py searches, filters and ranks real inventory rows in plain Python. The model is handed that finished list and asked for prose. If you deleted the LLM call entirely, the flight options a traveller sees would be byte-identical — only the wording would degrade.

Keep that in mind as you read, because almost every design oddity below exists to protect it. When you find yourself asking "why is this so defensive?", the answer is almost always: because the alternative lets a model's sentence become something a traveller tries to book.

01

Where the node lives

The Flight Agent is one node in a LangGraph workflow — one peer among four specialists, all of which run before a fifth agent synthesises their findings.

A list-valued source in add_edge is LangGraph's barrier: the orchestrator will not start until all four specialists have returned. There are no conditional edges at this level — every specialist is a plain node, and they are peers.

Agents talk over a versioned A2A envelope, never raw dicts. The node's first act is to find its own request; its last is to put a response back on the bus.

A second address for the same node

Since a2a_standard.py shipped, this node is also reachable over the official Agent2Agent 1.x wire protocol: SpecialistAgentExecutor wraps flight_node in asyncio.to_thread and serves it at /a2a/flight_agent. The node itself is unchanged — same signature, same single fetch, same ranking. See frontendPlusOrchestratorExplained.html §16.

02

The seam: shared contract to flight contract

adapter.py is the only file that imports both schema worlds. The shared TravelRequest has country and city; flights need airport codes. to_flight_request fills the gaps and returns an AdaptedRequest carrying an unresolved: list[str] of everything it could not do.

Rule you will rely on constantly

Nothing in this agent raises on a planning shortfall. "No flights for this route" is an answer the orchestrator can negotiate around; an exception is not. The rule is stated in agent.py's module docstring and honoured all the way down to providers/base.py, where a timeout, an empty supplier response and an unroutable request all yield an InventoryResult with no items and a note saying why.

Deliberately not stripped

traveller_genders is passed through to the model, against the usual instinct to drop a protected attribute at the boundary. It exists solely so an XRAI bias audit can vary it and observe the LLM. No ranking code reads it, and test_flight_bias_audit.py asserts that deterministic ranking is byte-identical across genders.

03

The deterministic core

domain.py — pure functions. No I/O, no LangChain, no reaching for a data source. Two concepts here you must not confuse.

Hard filters exclude. Soft preferences only reorder.

_screen_item returns a list of reasons a row is out. An empty list means it is included.

prefer_direct, avoid_red_eye and a non-hard ArrivalPreference never appear here. They cannot exclude anything — they can only sink a row down the ranking.

The rank key is a lexicographic tuple, not a blended score

Then Python simply sorts on that tuple. Why a tuple and not a weighted score: each position is individually nameable, so agent.py can restate them to the traveller as selection_factors and be telling the truth. A blended float would make that restatement a lie.

The safety wrapper around a caller-chosen order

normalise_priority matters because the caller can be a model. Three rules, all enforced in code rather than trusted to the caller:

  1. Unknown names are dropped, not raised on. A bad component name should cost ranking precision, not crash the request.
  2. Omitted components are appended, never dropped, so the key is always a total order — a permutation can reorder results but can never make ranking nondeterministic.
  3. cost is forced last, wherever the caller put it. It is the only reliably-continuous component, so it is the only one that reliably breaks a tie.

The bool | None rule you will trip over

Load-bearing

wheelchair_assist_available and step_free_boarding are bool | None, and None means "this supplier does not publish it", not "unavailable". Seed rows state a real True/False; Duffel has no such field at all. Never collapse None into either boolean.

Three separate places treat it as a genuine third case:

  • domain.py does not exclude on it. Excluding on unknown would return zero flights to every wheelchair user the moment inventory came from a live feed — which reads as "no flights exist for you" rather than the truth, "we could not check".
  • Ranking sinks it, but only for the traveller who asked. _component_accessibility_verified leads the default order because a confirmed flight beats a cheaper unknown one for that traveller. It is inert for everyone else.
  • agent.py surfaces it as an explicit unverified limitation — separate wording from "not offered", because those are different facts and only one of them is a property of the flight.

Collapsing None would libel flights that do offer assistance, or let an unchecked flight read as checked. Both failures land on the traveller who can least afford to find out at the gate.

04

The mode gate — three execution paths

Resolved once at node construction, not per request, so the mode cannot change under a traveller mid-plan.

A2A request
flight_node(state) — finds its own request on the bus
Adapt
adapter.to_flight_request — shared contract into flight contract
Fetch once
provider.covers? → ToolContext / InventoryCache — exactly one provider call
Mode gate
FLIGHT_AGENT_MODE — structured · agentic · auto
structured Always single-shot. reasoning.run_flight_agent. The one-variable revert.
agentic Always open the tool loop. agentic.run_agentic_flight_agent.
auto — default Single-shot, escalating to the loop only when a leg comes back empty.

The escalation test is free

That is the whole reason auto is worth having. Whether a leg is empty is decided by pure Python over rows already in memory — no model call.

Why auto exists — the measurement

docs/flight_agent/mode-eval.md: the loop turned one unstocked-date scenario from 0 options into 6, and produced identical option counts everywhere else for 2–4 extra seconds. Making the loop the global default would tax every traveller for a benefit most of them never see. So the common path keeps single-shot latency exactly, and only the requests that would otherwise return nothing pay for the loop.

One capability check guards it. Not every chat model exposes tool calling, and since auto is the default, a model without it would otherwise turn an empty leg from a disappointing answer into a failed request:

Checked as a capability rather than caught as an exception — so the trace says what actually happened.

05

Inventory is fetched exactly once

provider.covers() is a cheap pre-check — "does this source have anything for this route at all?" — that avoids spending a network call or an LLM call on a route nobody stocks. The fetch itself goes through InventoryCache, so the single-fetch invariant lives in a component rather than in this function being careful.

The same ctx is passed into the loop. Building a second one there would re-fetch inventory the node has already paid for — free on seed, billed on Duffel.

What InventoryCache guarantees

  • Deduplication by key. Two searches with the same parameters cost one provider call.
  • Static providers collapse to one key. Seed returns its whole dataset regardless of request, so is_static makes every key "*" — the entire loop costs exactly one call however many times the model searches. A property the class states and a test asserts, rather than a fact about seed that callers have to know.
  • seen_ids is the provenance ledger, populated here and nowhere else. If tools registered ids themselves, the guarantee would depend on every tool remembering to — and the one that forgot would be the hole.
  • It never returns empty when rows exist. Out of budget, it returns everything already seen plus a note saying why it is not more. "We stopped searching" and "there are no flights" are different answers, and only one of them is about the traveller's trip.
06

Path A — the single-shot structured path

This is the default, and it is the structured output agent pattern, not a loop. The tool always runs first and is never bypassed.

Structured output

The model cannot return free text — it must return a validated FlightAgentResponse. Note that _build_messages uses plain dicts, not LangChain message objects. That is deliberate: this module stays importable without LangChain so the grounding and fallback logic is testable without the dependency.

Retry-then-fallback, fail-closed

A hallucinated flight ID, an exception, and a bias- or toxicity-flagged rationale all land in the same bucket: retry once, then hand back the deterministic proposal with a canned sentence. The flights survive; only the prose is lost.

"Option B" — bounded relaxation

The model may propose relaxing one soft preference. It never decides one. Two fences, neither of them the prompt:

  1. The schema is the fence. PreferenceRelaxation.field is a three-value Literal. A request to relax max_stops, budget, a hard arrival deadline, or accessibility cannot even be expressed — Pydantic rejects it before domain.py ever sees it.
  2. Re-verification in code. domain.relaxation_is_valid(relaxation, gaps) confirms a real gap exists. The model's own claim that relaxing something would help is never trusted.

If both fences pass: one extra tool call, one extra LLM pass, and the response is stamped with relaxation_applied so the traveller is told. Bounded, not a loop. Anything else is ignored rather than applied, and traced as agent_relaxation_rejected.

Note on gaps

preference_gap_for_leg deliberately returns an empty list when a leg has no survivors at all. An empty leg is a hard-constraint problem — accessibility, seats, dates, max_stops, a hard deadline — and never something soft-preference relaxation is allowed to touch. That case must go to escalation instead.

07

Path B — the agentic tool loop

This is where the actual agentic machinery lives. Three files cooperate: tools.py (the callable surface), agents/loop.py (the budget and cache), agentic.py (the graph).

The separation that makes a loop safe here

The model decides what to search, how to rank and whether to relax. It never decides what a flight says.

7a · domain.py exposed as three tools

ToolWhat the model gets to decide
search_flightsWhat to search — shift a leg date, or restrict to specific airports
rank_flightsHow to rank — permute precedence between named components
relax_constraintWhether to relax — propose one soft preference

TOOL_SPECS is hand-written OpenAI-format dicts, not @langchain_core.tools.tool decorators. bind_tools accepts those dicts directly, which keeps the LangChain edge confined to agentic.py alone — a boundary tests/test_flight_imports.py enforces.

7b · The argument envelope — the actual fence

A prompt asking the model to stay near the traveller's dates is a request. This is a guarantee.

Two details worth internalising:

  • Measured against the base request, never the current one. Otherwise three successive ±3 shifts walk to ±9 and the traveller's Tuesday quietly becomes next week.
  • Airports must be a subset of what airports.resolve_route already resolved. The model may prefer HND over NRT for Tokyo; it can never search JFK. The traveller chose cities — searching outside that set answers a different question than the one asked.
The pattern that keeps the loop alive

A violating call returns a refusal dict to the model. It does not raise. The model reads it, corrects itself, and the loop survives. _refusal sends detail to the model but only reason_code to the audit trail — the trace holds codes and counts, never free text.

And when a leg comes back empty, the tool hands back something the model could not have reasoned its way to — the dates this route actually flies, derived from real rows:

7c · LoopBudget — four caps and a clock

  • Every spend_* returns False instead of raising, and callers turn that into a refusal the model can conclude from.
  • fresh() turns node-lifetime limits into per-request mutable state. Spend must never be shared between travellers.
  • expired() is wall-clock, not turn count — the flight node sits on a fan-out branch behind a barrier edge, so the whole plan waits for the slowest specialist. A loop that is slow for any reason must still hand back.
  • max_provider_calls bounds calls to fetch, not supplier searches: duffel.fetch fans out over airport pairs and one call can mean several billed POSTs. Sized accordingly rather than renamed, because fetch is the only unit the module can observe.

7d · The subgraph

That is a textbook ReAct loop: plan → (tool calls? → act → back to plan) : END.

Note the budget-exhausted trick: returning an empty AIMessage means "no tool calls", which _should_act already routes to END. No second termination signal is needed.

Why a subgraph, not tools_condition on the main graph

The outer graph is a fan-out of four peers with no conditional edges. Putting a tool loop at that level would make one specialist's internals part of the workflow every other agent runs through. The loop is an implementation detail of one node, so it lives inside one node.

7e · The terminal turn is structured, always

The loop ends in tool-call land, but what leaves the module must be a FlightAgentResponse. So the last call happens outside the graph — which is also the answer to "a bound-tool invoke returns tool calls, not a schema".

Same retry-then-fallback contract as the single-shot path. Retries apply to the terminal turn only, so the worst case is max_llm_turns + MAX_ATTEMPTS model calls rather than max_llm_turns × 2.

The grounding gate here is the widened one — validate_grounded_ids(ids, ctx.cache.seen_ids) rather than membership in the final proposal. A flight found in an earlier search but ranked out of the final three is legitimately discussable; anything outside seen_ids was never returned by a provider and is a fabrication.

7f · And then code takes back over

final_proposal re-ranks deterministically via rank_leg under whatever ordering the model legitimately chose. With no choice expressed it is exactly propose_flights — which is what keeps the golden scenarios valid.

date_shift_notes() matters ethically, not just technically: moving a traveller's date without telling them would be worse than returning nothing. And only a search that found something moves the leg — a widened search that also came back empty leaves the traveller's own date in place, so the coverage warning still names the date they asked for.

The four things that keep the loop safe

None of them is the prompt.

  1. The argument envelope. tools._validate_search_args caps how far a search may move a date and which airports it may use.
  2. LoopBudget. Caps model turns, tool calls, provider calls and wall clock.
  3. domain.py owns ranking. rank_flights permutes precedence between named components; it cannot invent one or drop a tiebreaker.
  4. agent.py builds every Option from proposal.candidates — produced by code over rows the cache actually returned. The model's message never becomes a flight.
08

Path 2 — the no-inventory fallback

When nothing covers the route — an unstocked route, an unroutable country, or a live search that failed or came back empty — the node falls back to the shared prompt-only specialist every other agent uses.

Here is the part worth understanding. With no inventory, validate_grounded_explanation cannot run: the candidate set it tests membership against does not exist. And a fabricated option in options is exactly what the UI renders most prominently. Disclosure alone was too weak a control, so the postprocess strips every option:

The prompt (PATH2_INSTRUCTION) asks the model for the same thing — route-level guidance, no flight numbers, no fares. But a prompt is not a correctness guarantee, which is exactly why the stripper exists. The prompt states the intent; the postprocess is the guarantee.

Order matters: prose that fails bias/toxicity/injection screening is replaced wholesale by a canned finding that carries no options, rather than being stripped and kept.

Do not reword this casually

ESTIMATE_WARNING carries the substring safeguards.UNVERIFIED_OPTIONS_MARKER matches on. Reword or drop it and enforce_provenance_disclosure silently stops firing — the plan loses its unverified-data flag, with nothing failing loudly to tell you.

09

Guardrails — two layers, don't confuse them

LayerWhereWhat it does
Shared L2travel_ai/guardrails/specialist.pymake_preflight / make_postprocess, used by prompt-only nodes
Flight's ownflight_agent/guardrails.pyInjection / bias / toxicity screening, plus flight-ID grounding

Flight's own layer runs three checks on input before the model sees it, the same two detectors on the model's rationale, and validate_grounded_ids for flight-ID grounding. The input gate runs before any search, so a blocked request costs nothing.

Bias screening is deliberately two-tier

A protected-attribute mention alone is medium and passes; attribute plus a stereotype trigger is high and blocks. Travel content legitimately mentions nationality, religion and culture — only stereotyping is the problem.

Toxicity terms are word-bounded, not substring

A bare in test fires "kill" on Kilimanjaro and "die" on Dieppe.

One subtlety in dispatch

It catches TypeError — but never a SafetyError or a guardrail exception. Those are fail-closed by design, and swallowing one would convert a blocked request into an allowed one.

The import boundary

agentic.py is the only module in the flight package permitted to import LangChain or LangGraph. domain.py, guardrails.py, reasoning.py, schemas.py and tools.py are deliberately free of it, so the grounding layer stays testable without the dependency. tests/test_flight_imports.py enforces it, and this module is the intended exception.

One more pattern worth naming

The traveller's request goes into a HumanMessage, never interpolated into the system message:

That is the pattern agents/base.py established and the semgrep rule llm-untrusted-data-in-system-message enforces: mixing the two lets a traveller's free-text preference edit the agent's instructions.

Before you push

pytest -q. Tests never call a live model. Golden scenarios are pinned to seed output — a change to ranking or seed data will move them, and that is the point. Re-pin deliberately, never reflexively.
